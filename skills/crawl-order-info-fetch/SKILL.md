# Fetch raw order info

This plugin has **no database access**. It cannot resolve an order_number to its shop/platform on its own — the caller must supply:
- `platform_id` (numeric) or a platform domain string (e.g. `zalora.sg`, `tiktok.id`) — see `scripts/crawl_data_config.py`'s `PLATFORM_IDS` for the full list. Platform IDs are **per-country**, not per-marketplace-brand: Lazada, Zalora, Shopee, and TikTok each have a distinct ID per country (e.g. TikTok Indonesia=403, Thailand=405, Vietnam=400 — don't assume one ID covers "TikTok" generally).
- `shopfe_id` (the shop's frontend id in PowerSell, i.e. `--shop-id` below).
- `env` (`dev`/`staging`/`prod`).

If any of these are missing, **ask the user** rather than guessing — a wrong `platform_id` for a given `shopfe_id` returns either an unrelated shop's data or a hard error (e.g. HTTP 500), not a helpful "wrong platform" message.

1. **Determine request_type** for the (category, platform) pair from the verified matrix in `references/request-type-matrix.md`. The request_type name and params shape vary per platform — check the matrix before assuming a name.

   **For a single specific order ("raw data for order X"), always prefer the `get_orders_items`/`get_order_items` variant over `get_orders`/`get_order` when the platform has one** (Lazada, Shopee, TikTok, Shopify, Qoo10 all do) — the items variant returns item-level fields (e.g. Lazada's `order_type`, `shipping_type`, `shipping_provider_type`) that the plain order-header call omits. Only fall back to `get_order`/`get_orders` when no item-level variant exists for that platform (Bagisto, Haravan, Mirakl), or when the user explicitly just wants the order header. Verified request_types so far: Zalora/Shopee/Lazada/TikTok/Shopify → `get_orders_items` + `params.scOrderNumber` array; Qoo10 → `get_order_items` + `params.scOrderNumber` array (plain order-number strings, not comma-joined — that's the older `get_shipping_and_claim` variant); Mirakl → `get_order` (singular, already full detail, no item-level variant); Bagisto → `get_order` (no richer alternative); Haravan → `get_order` (singular, one API call per order number in `params.scOrderNumber`).

   **Return support varies a lot by platform — check the matrix in `references/request-type-matrix.md` before assuming a category exists.** Shopify/Bagisto/Haravan/Mirakl have no return endpoint at all; Qoo10 has no dedicated return endpoint either (return data is mixed into `get_orders_claim`'s claim-status list, not fetchable per-order).

   **For transaction, use the `crawl-transaction-fetch` skill instead** — not covered here. It's a different query shape (date-range, not order-number) and the obvious request_type name (`get_wallet_transaction_list`) is wrong for 3 of the 4 platforms that have one at all (Lazada/Shopee/TikTok/Zalora; Bagisto/Haravan/Mirakl have none).

   **Shopee order — deliberately staying at 1 call, not 3.** The real production pipeline (`ShopeeApiV2Parser_GetOrder.php::parse_get_orders_items`) actually makes 3 calls per order: `get_escrow_detail_batch` (real seller payout/income, different from `payment.total_amount`) before `get_orders_items`, then conditionally `get_tracking_number` (skipped for `UNPAID`/`READY_TO_SHIP`/`CANCELLED`/`IN_CANCEL`). Decided **not** to add these to raw-data fetches by default — `get_orders_items` alone is enough for "raw data for order X". Only reach for `get_escrow_detail_batch` if the user specifically asks about seller payout/income (a different number than what's in the order response).

   **Shopee seller payout/income — 3 escrow request_types exist, only one is the production one.** `ShopeeRequestV2_GetOrder.php` defines all three:
   - **`get_escrow_detail_batch`** (production — what `parse_get_orders_items` actually calls) — POST `/api/v2/payment/get_escrow_detail_batch`, `params.scOrderNumber` (array, chunked 50/call → `order_sn_list`). Response is an array of `{escrow_detail: {order_sn, order_income: {items: [...], voucher_from_seller, voucher_from_shopee, ...}}}` per order — this is the one to use for "raw payout/income for order X", including batches of orders.
   - **`get_escrow_detail`** (exists, NOT what production uses) — GET `/api/v2/payment/get_escrow_detail`, same `scOrderNumber` param but 1 API call per order (`order_sn` singular, looped) instead of batched. Functionally overlapping with `get_escrow_detail_batch`'s per-order data — no reason to prefer this one, it just costs more calls for multiple orders. Don't pick it by name-guessing over the batch variant.
   - **`get_escrow_released`** — a different concept, shop-level release list by date range (`pagination_info` → `release_time_from`/`release_time_to`), not per-order. This is the one documented in `crawl-transaction-fetch` — use that skill instead when the ask is "settlement/payout for shop X over a date range" rather than "payout for order X".

   **Shopee tracking number — only fetch when explicitly asked.** request_type `get_tracking_number` (Shopee V2, `ShopeeRequestV2_GetOrder.php::make_get_tracking_number`) → GET `/api/v2/logistics/get_tracking_number`, `params.scOrderNumber: [orderId]` — one API call per order (the template loops and calls once per id, same pattern as `get_escrow_detail`). Skip it for orders in `UNPAID`/`READY_TO_SHIP`/`CANCELLED`/`IN_CANCEL` status — verified in `ShopeeApiV2Parser_GetOrder.php` (`$isValidGetTrackingNumber` check), there's no tracking number yet at those statuses so the production parser doesn't even attempt the call. Don't set `auxiliary` for a raw-data fetch: production sets it to `GET_TRACKING_NUMBER_ONE_TIME_ONLY`, which makes request-maker-v5 check an internal DB cache first and skip the marketplace call for orders it already has a tracking number stored for — fine for the recurring pipeline, but a one-off "get raw tracking number for order X" ask should always hit the marketplace fresh, so leave `auxiliary` unset.

   **Shopee logistics channel list (`get_logistics`) is shop-level, not order-level.** `make_get_logistics` (Shopee V2, `ShopeeRequestV2_GetLogistic.php:24`) takes **no params at all** — direct pass-through to `/api/v2/logistics/get_channel_list`. Don't pass `scOrderNumber`/`pagination_info`, they're ignored. Response is `response.logistics_channel_list[]` (one entry per shipping provider configured for the shop: `logistics_channel_id`, `enabled`, `cod_enabled`, `weight_limit`, `item_max_dimension`, plus a long `logistics_description` marketing-text field). Runs 30-50KB for shops with many channels. The exact function name `make_get_logistics` also exists for JD/Shopee V1/Zalora/Tokopedia but **not verified** whether those return the same shop-level channel-list concept (Zalora's lives in `ZaloraRequest_GetOrder.php`, suggesting it might be order-scoped instead) — check that platform's actual implementation before assuming symmetry.

   **Lazada shipment trace — `get_order_trace`, exists but not used by production.** `LazadaRequest_GetOrder.php::make_get_order_trace` — GET `/logistic/order/trace`, `params.scOrderNumber: [orderId]` — one API call per order (`order_id` singular, looped). Registered and freely callable, but no crawler parser consumes it — so unlike the Shopee tracking-number/escrow cases above, there's no production code to cross-check the response shape against. Use it if the user specifically asks for Lazada shipment trace/tracking history, but treat the response fields as unverified until you've actually seen one.

   **Lazada `get_orders_items` has no address/postal code at all** — verified empirically (order 509022047176909): the `/orders/items/get` response has item/pricing/logistics fields but no `address_billing`/`address_shipping` object whatsoever. That address data (incl. `post_code`, name, phone) only comes from `get_order` (singular, `/order/get`, `params.scOrderNumber`) — the plain header call this skill's general rule says to *skip* in favor of `get_orders_items`. So for Lazada specifically: keep using `get_orders_items` as the default for "raw data for order X", but if the ask involves recipient address/postal code/phone, call `get_order` (singular) too — `get_orders_items` alone won't have it. Not yet verified whether this same gap exists on other platforms' `_items` variants (Shopee/TikTok/Shopify/Zalora) — check empirically before assuming either way.

2. **Call the script**, picking the right environment:
   ```
   python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fetch_crawl_data.py \
     --env dev|staging|prod \
     --platform-id <platformId> --shop-id <shopfeId> \
     --request-type <type> --params '<json>'
   ```
   (`--base-url` also works if you need a URL not in `scripts/crawl_data_config.py`'s `DEFAULT_BASE_URLS`.)

3. Reply following the `crawl-data-reply` skill.
