**General rule: for raw data on one specific order, always prefer the `get_orders_items`/`get_order_items` variant (when the platform has one)** over plain `get_orders`/`get_order` — the item-level variant returns item-level detail (e.g. Lazada's `order_type`, `shipping_type`, `shipping_provider_type`) that the header-only call omits. Confirmed empirically on a Lazada order (`get_order` had no `order_type`, `get_orders_items` did). Applies to Lazada, Shopee, TikTok, Shopify, Qoo10 (all have an item-level variant); Bagisto/Haravan/Mirakl only have one variant (no richer alternative); Zalora always uses `get_orders_items` for single-order requests (no real `get_single_order`).

**⚠️ Lazada return correction:** `make_get_returns` (`/reverse/getreverseordersforseller`) only lists by date range (`pagination_info`) — it does **not** accept a `reverse_order_id` filter (verified by reading `LazadaRequest_GetReturns.php`). The correct request_type for one order's raw return is `make_get_order_return_by_id` (`/order/reverse/return/detail/list`, `params.scOrderNumber: [reverse_order_id]` — get `reverse_order_id` from `get_order_return_info` (mcp-db) or the `reverse_order_id` field in `get_orders_items`'s response, not `order_number`). Verified against real order `1108984565305941` (Lazada Philippines).

**⚠️ Transaction correction:** `get_wallet_transaction_list` exists on Lazada/Shopee/TikTok but is **not** what the parser actually uses (confirmed by reading the real `parse_get_transactions` in `crawler-v3-golang`, not guessed from the name) — Lazada uses `get_transaction_details` (fee-level), Shopee uses `get_escrow_released`/`get_escrow_detail` (defined in `ShopeeRequestV2_GetOrder.php`, not a "transaction"-named file), TikTok needs two chained calls `get_statements` → `get_statement_transactions` (its `get_wallet_transaction_list` is actually withdrawal events, a different concept). Full per-step endpoint/param detail: `crawl-transaction-fetch/SKILL.md`.

Param shape reference: `cmd/worker/parsers-php/include/data/Config.php` (`pagination_info`, `scOrderNumber`, ...) — the shared contract both `request-maker-v5` and the PHP parser use.

**Qoo10 note**: every category tends to split into several smaller request_types by status/data-type instead of one combined endpoint (order list split by shipping/claim status, transaction split into 5 settlement types) — unlike the "1 request_type = 1 category" pattern on other platforms. Keep this in mind for any auto-selection logic.

**Mirakl note**: two methods exist in code but are **not** registered in `$request_types` (`make_get_import_offer_report`, `make_process_orders_full_cancel`) — not reachable through normal dispatch, possibly unfinished or deprecated. No action needed, just a note.
