# Transaction request_type reference

Found by reading the actual `parse_get_transactions` parser code per platform, not by guessing from method names — the obvious name (`get_wallet_transaction_list`) is wrong for 3 of the 4 platforms below.

| Platform | request_type to use | Endpoint | Params | What `get_wallet_transaction_list` actually is instead |
|---|---|---|---|---|
| **Lazada** | `get_transaction_details` | GET `/finance/transaction/details/get` | `pagination_info` (date range) + optional `scOrderNumber: [orderId]` (only the first element is used, via `trade_order_id`) | A real, separate endpoint (`/finance/transaction/accountTransactions/query`, POST) — untested against what the parser actually needs, don't use it for "raw transaction" requests. Also note `get_transaction_details_v2` exists and is byte-for-byte identical code to `get_transaction_details` (a duplicate, not a newer version) — either works, prefer the non-`_v2` one since that's what the parser calls. `get_payout_status` is a third, distinct one (payout/statement level, date-only) — don't confuse it with transaction-level detail. |
| **Shopee V2** | `get_escrow_released` (range) or `get_escrow_detail` (specific orders) | GET `/api/v2/payment/get_escrow_list` (range) / GET `/api/v2/payment/get_escrow_detail` (per order) | Range: `pagination_info` → `release_time_from`/`release_time_to`. Per-order: `scOrderNumber: [orderId, ...]` → `order_sn` (one API call per order — the parser loops and calls once per id). Both templates are defined in `ShopeeRequestV2_GetOrder.php`, not any file with "transaction" in its name — don't rely on grepping filenames for this one. | `get_wallet_transaction_list` (`/api/v2/payment/get_wallet_transaction_list`) is a real, separate wallet-ledger endpoint — the parser's `parse_get_transactions` never calls it. |
| **TikTok** | `get_statements` then `get_statement_transactions` (two sequential calls, not one) | Step 1: GET `/finance/{ver}/statements` (range, paginated) → returns a list of statement ids. Step 2: for each statement id, GET `/finance/202501/statements/{statementId}/statement_transactions` | Step 1: `pagination_info` (date range + pagination). Step 2: `auxiliary` = JSON-encoded array of statement ids from step 1 (e.g. `"auxiliary": "[\"7123...\"]"`), plus `pagination_info` for its own paging. This mirrors exactly what `TiktokParser_GetTransactions.php`'s `parse_get_transactions`/`getStatementTransaction` do — list statements, then page through each statement's transactions. | `get_wallet_transaction_list` (`/finance/{ver}/withdrawals`, types `WITHDRAW,TRANSFER,SETTLE,REVERSE`) is **withdrawal/payout events**, a different concept entirely from per-order transaction fee breakdown — don't substitute it thinking it's a simpler one-call alternative. |
| **Zalora** | `get_transactions` | GET `/v2.1/finance/transactions` | `pagination_info` → `gteCreatedAt`/`lteCreatedAt` (ISO8601), `limit`/`offset`, sorted by `createdAt desc` | `get_transaction_details` (GET `/v2/seller/payout`, date-only) is the older payout-level endpoint — still a real, valid call, just a different, coarser concept (payout batches, not per-order transactions). The parser (`ZaloraApiParser_GetTransaction.php`) calls `get_transactions`, not this one. |

Haravan, Bagisto, Mirakl have **no transaction endpoint at all** — don't look for one; say so directly if asked.

## TikTok — a 3rd finance method exists: `get_settlements`

`TiktokRequest_GetFinance.php::make_get_settlements` — POST `/api/finance/settlements/search`, `pagination_info` (`updated_from`/`updated_to` → `request_time_from`/`request_time_to`, defaults `request_time_to` to now if omitted) + cursor-based paging (`pagination_info` → `payload.cursor`/`payload.page_size`), fixed `payload.sort_type` (`DEFAULT_SORT_TYPE_SETTELMENT`, no need to pass it yourself).

**Confirmed NOT called by `parse_get_transactions`** (`TiktokParser_GetTransactions.php` only calls `get_statements`→`get_statement_transactions`, verified by reading the actual `buildRequestConfigAndCall` calls) — this is a separate, real, registered request_type (`TiktokRequest.php:119`) that the production transaction pipeline doesn't use. Settlements are payout-batch level (like Lazada's `get_payout_status` or Zalora's `get_transaction_details`/payout endpoint), a coarser concept than the per-order transaction fee breakdown from `get_statement_transactions`. Use `get_settlements` only if the ask is specifically about payout/settlement batches rather than per-order transaction detail — default to the documented `get_statements`→`get_statement_transactions` flow for a plain "get transactions for shop X" request.
